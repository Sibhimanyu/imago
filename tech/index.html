Imago: APIs become interfaces

Paste the URL of any public JSON API. Imago fetches it, works out the shape of the response, designs a page for that shape, remembers the design, and watches the endpoint change over time. One app, where getting, remembering and time are the product rather than three demos on one page.

01

The brief, and the idea

Build a small web app that gets something from the internet, remembers something, and does something because time has passed. HTML, CSS and JavaScript only, browser storage only. It should feel like one complete thing.

What it helps someone do

Understand an API's data in seconds, and see when it changes.

Developers meeting a public API paste its URL into a tab and scroll raw JSON. Imago draws the page that data deserves instead.

Ideas I weighed first

Internet Terrarium, Orbiting Dead Drop, API Time Machine, Anti-Feed, Internet Sensor Board, Internet Alarm Clock, JSON Archaeologist.

I skipped the weather app, movie tracker and recipe box on purpose.

Why this one

It is the only idea where all three behaviours are one loop: every fetch is compared with what was remembered, and time is what makes the comparison worth doing.

It started as Morph. It became Imago: Latin for image, and the final stage an insect reaches after metamorphosis. Raw JSON goes in; its finished form comes out.

02

Get, remember, time: one loop

Each behaviour feeds the next. A fetch is fingerprinted; the fingerprint decides what is remembered; time brings the next fetch, which is compared with what was remembered.

Get

Any public GET endpoint, and a model

  • Paste a URL, or a curl command copied from API docs or dev tools.
  • The response's shape (values replaced by types) is hashed into a fingerprint.
  • A model (Gemini or Groq, with your own key) designs a page for that shape. With no key, rules design it.
  • When a request fails, Imago says why in plain words: offline, server down, or an API that does not allow browser apps (CORS), told apart with one extra probe.
Remember

Five stores, all in the browser

  • Designs by shape (imago.schemaSpecs). The model is asked once per shape; every later response of that shape reuses the design for free.
  • Saved endpoints, with when each was last opened.
  • Snapshots: the last 10 fetches of each endpoint, the newest with its body.
  • Your edits to a page (rename, move, hide a field), kept per shape.
  • Where you were: reopening the tab rebuilds the last page from its snapshot, with no request.
Time

Watch an endpoint change

  • Watch re-fetches every 10, 30 or 60 seconds, with a live countdown.
  • Each fetch is diffed against the previous snapshot; changed values are marked CHANGED on the page.
  • A history strip puts one tick on the timeline per fetch, yellow where something moved.
  • "Checked 12s ago" stays honest while idle. In another tab, the title counts changes ("(3) Forecast") and a notification can say what moved.
03

How it works

The model never writes HTML, CSS or JavaScript. It returns a small JSON plan, and Imago's own renderer turns the plan into DOM, writing every value with textContent.

Fetch

fetch() the URL with your headers, abortable, 30-second timeout.

Fingerprint

Replace every value with its type, sort the keys, hash it: sch_1ouax1u.

Seen this shape?

Yes: reuse the stored plan, no model call. No: ask before spending one (a Generate button).

Plan

The model, or the rules, return a JSON plan: which fields, which components.

Validate

Every plan (model, rules or share link) is normalised: unknown types dropped, paths checked, at most 20 components.

Render

15 components (metric, table, chart, stat bars, timeline, gauge…) drawn by the app, never by the model.

Snapshot

Store the fetch, keep 10 per endpoint, only the newest with its body.

Diff

Flatten both bodies to paths, compare, mark what changed.

A plan, as the model returns it

{
  "title": "Pikachu",
  "titlePath": "name",
  "layout": "profile",
  "components": [
    { "type": "image",    "path": "sprites.front_default" },
    { "type": "metric",   "path": "base_experience", "emphasis": "hero" },
    { "type": "badges",   "path": "types", "itemPath": "type.name" },
    { "type": "statBars", "path": "stats",
      "labelPath": "stat.name", "valuePath": "base_stat", "max": 255 }
  ],
  "actions": [{ "type": "follow", "path": "species.url", "label": "Species" }]
}

Without any AI

With no key, the same pipeline runs with rules in place of the model. They read the data's shape, never an API's field names:

  • short lists of name + number become bars; lists of names become badges; other lists become tables
  • numeric arrays that line up with timestamps become charts; three or more timestamps become a timeline
  • answers nested under current or results are lifted up, with units from a matching _units object
  • IDs, versions and offsets fold into Details

The Pikachu, ISS and weather pages on this report were all drawn this way.

04

Decisions, and why

The brief says there is no single correct way to build it. These are the calls I made.

DecisionWhy
The model returns a plan, not a pageAPI data and model output are both untrusted. A JSON plan can be validated and rendered safely; generated HTML could carry scripts. A full-HTML mode exists as an option, sandboxed, and may only load URLs already in the data.
Remember designs by shape, not by URLEvery Pokémon has the same shape, so one design serves them all, and a model call is spent once per shape. The title is read from each response (titlePath), so Ditto is never titled "Pikachu".
Ask before spendingA new shape shows a Generate button instead of calling the model on its own, so a key is never spent without a click.
Works with no keySomeone opening the app for the first time sees a real page on the first try, not a key form.
Browser only, no serverThe brief asks for browser storage, and it keeps keys on the user's machine. The cost is accepted: APIs that block browser apps (CORS) cannot be read, and the app says so plainly.
Credentials stay in the sessionRequest headers such as Authorization live in sessionStorage, and what they fetched is not written to snapshots. Keys in a URL are removed from share links and masked in prompts.
Native ES modules, no build stepNo framework, as the brief asks, and no bundler either: the browser loads js/main.js and its 15 sibling modules directly. A static server is the whole deployment.
A Content Security PolicyNo inline scripts; fetches only to https, plus plain http on localhost for an API on your own machine. The app also refuses to run inside another site's frame.

06

How I know it works

A test suite is what made it safe to change this much in a week.

433 tests

25 files, Vitest with jsdom. The suite boots the real app in a fresh page for every test.

Mutation-checked

Every bug fix gets a test, then the fix is broken on purpose to prove the test fails. This caught three tests that passed whatever the code did.

83% of lines

Measured on the real modules, not the test harness. The rendering code is the gap.

An audit, and 30 fixes

On 24 September I ran a security review, a correctness hunt and a hands-on browser QA pass against the app. They found 30 problems. Each was fixed with a regression test, and all 41 deliberate breaks of those fixes turned the suite red (v0.13.0.0). The worst:

CORRECTNESS

A remembered design kept the title of the response it came from. Open Ditto after Pikachu and the page said "Pikachu". The plan now names the field its title comes from.

CORRECTNESS

A slow request locked the app. Clicks were ignored until it failed, and the URL you had typed was lost. A new request now replaces the old one, which is aborted.

SECURITY

A generated HTML page could send data out. An image URL written by the model could carry the response to another site. The page may now load only URLs already in the data.

SECURITY

Keys in the address leaked. ?api_key= went into share links and model prompts. It is now removed from links and masked in prompts.

What I left out, on purpose

  • POST, PUT, DELETE. Imago reads data; sending it is Postman's job, and a GET is safe to repeat on a timer.
  • A proxy server to get around CORS. It would route people's data and keys through a machine I run.
  • Accounts and sync. They need a server, and the brief asks for browser storage.
  • A framework. The brief rules it out, and 16 small modules did not need one.
08

Known limits, and tools used

Known and left open

  • APIs that block browser apps cannot be read. This is by design.
  • Without a model, the rules cannot know a unit the API does not state: PokeAPI's height is in decimetres, and the ISS altitude above is shown in degrees though it is kilometres.
  • The remembered designs have no size limit yet.
  • Some touch targets are under 44px on phones.

The open list lives in TODOS.md.

Tools used

Claude (Claude Code) wrote most of the code with me, with the gstack skills for QA, review and shipping. The idea, the three-behaviour loop, the plan-not-HTML rule and the calls in section 04 were decided in conversation, and I rejected plenty of its first answers.

Figma holds the design, kept in sync with the shipped app. Google Gemini and Groq are the model providers users can choose. Zoho Catalyst Slate hosts the app.
